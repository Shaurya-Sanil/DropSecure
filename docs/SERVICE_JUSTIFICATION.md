# AWS Service Justification & Architectural Tradeoffs

This document details the architectural decisions for each AWS service utilized in **DropSecure**, explaining the rationale for adoption, rejected alternatives, and failure impact.

| AWS Service | Why This Service? | Rejected Alternative | What Breaks / Suffers Without It? |
| :--- | :--- | :--- | :--- |
| **Amazon VPC (Public & Private Subnets)** | Provides strict network segmentation. Places RDS and Lambda inside private subnets with no internet routability, shielding sensitive verification data and hashes. | Single flat public subnet; Direct internet exposure with firewall rules only. | Database port 5432 exposed to internet scanning; zero-day exploits in PostgreSQL or brute force attempts reach DB directly; fails enterprise security standards. |
| **Amazon EC2 (t3.micro)** | Cost-effective compute for hosting the continuous Node.js Express REST API and persistent SQS background polling worker with systemd/PM2 supervision. | AWS Fargate / ECS; AWS App Runner; Kubernetes (EKS). | Fargate/ECS adds task provisioning overhead and higher continuous minimum cost outside the free tier; EKS is massively overengineered and costly ($72/mo for control plane alone). |
| **Amazon RDS PostgreSQL (db.t3.micro)** | ACID-compliant relational model with strict foreign keys, transactional integrity for verification states, and automated backups/patching. | DynamoDB (NoSQL); Self-hosted PostgreSQL on EC2. | DynamoDB makes complex relational queries (sweep query with multi-condition date joins, audit trails) cumbersome and prone to data inconsistencies during concurrent OTP attempts; self-hosted PostgreSQL lacks automated snapshots, automated failover, and increases sysadmin burden. |
| **Amazon S3** | High-durability (99.999999999%), highly scalable object store for parcel photo proofs. Direct client uploads via presigned URLs keep API server bandwidth and memory footprint minimal. | Storing binary images directly as BLOBs in PostgreSQL; saving files to local EC2 EBS volume. | Storing images in DB balloons database size and backup windows; storing on EC2 disk exhausts EBS volume, prevents horizontal scaling of EC2 instances, and loses images if the instance terminates. |
| **Amazon SQS + DLQ** | Decouples the drop-off API from the cryptographic hashing and email dispatch operations. Guarantees message persistence even under network spikes; DLQ isolates malformed messages after 3 retries. | Synchronous inline processing inside the POST /api/parcels handler; Redis Pub/Sub; RabbitMQ. | Delivery partner phone waits 2–5 seconds while OTP is hashed and SNS sends emails; if email service slows or fails, the parcel creation fails completely; lacks built-in DLQ retry semantics without complex Redis scripting. |
| **Amazon SNS (Topic + Subscription Filter Policy)** | Managed pub/sub notification service with fanout capabilities. Attribute filtering (`recipientId`) ensures strict isolation so subscribers only receive notifications for their own parcels. | Direct SMTP (SendGrid/Nodemailer via EC2); AWS SES direct send. | Direct SMTP ties server to IP reputation, risks spam blacklisting, and requires complex retry logic; SNS filter policies offload message routing from application code to AWS managed infrastructure. |
| **AWS Lambda** | Serverless compute executed strictly once a day (or on-demand). Incurs zero idle compute cost. Queries RDS and publishes stale parcel warnings. | Continuous cron job running 24/7 on EC2 or a dedicated worker instance. | Consumes continuous memory and CPU on EC2 for a 5-second daily task; risks failure if the EC2 instance restarts or freezes at scheduled execution time. |
| **Amazon EventBridge** | Serverless cron scheduler providing millisecond-accurate scheduling (08:00 AM IST) directly invoking the Lambda function without server maintenance. | Linux cron (`crontab`) on EC2; Node.js `node-cron` in-memory schedule. | In-memory cron dies when the server restarts or scales; no CloudWatch execution metrics or dead-letter queue routing for failed schedule triggers. |
| **AWS Systems Manager (SSM) Parameter Store** | Secure, centralized, encrypted (`SecureString` via AWS KMS) storage for database passwords and JWT secrets. EC2 and Lambda fetch credentials at runtime using IAM roles. | Storing secrets in plain `.env` files in git repository or EC2 filesystem. | Plaintext credentials on disk risk exposure through repo leaks, unauthorized SSH access, or server backup dumps; violates college and industry compliance frameworks. |
| **AWS IAM (Instance & Execution Roles)** | Least-privilege role-based access control. Grants temporary STS credentials to EC2 and Lambda without storing long-lived AWS Access Keys on the filesystem. | Hardcoding `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` in environment variables. | Leaked access keys grant persistent, account-wide attack surface; IAM roles eliminate key rotation overhead and enforce time-bound permissions. |
| **Amazon CloudWatch** | Unified operational monitoring: logs for API, Worker, and Lambda; custom metrics for dropped parcels and OTP failures; automated alarms for EC2 CPU, DLQ backlog, and budget overruns. | Self-hosted Prometheus + Grafana; Logstash/ELK stack. | High memory footprint and hosting cost ($15–$30/mo minimum) for ELK; CloudWatch is native, zero-setup, and integrates seamlessly with AWS free tier. |
| **AWS Budgets** | Proactive financial guardrail configured with email alerts when forecast spending exceeds $1.00 USD. | Manual daily AWS billing dashboard checks. | Unexpected billing spikes from orphan resources or infinite loops go unnoticed until end of month; essential for student credit budgets. |

## Architectural Principles Applied

1. **Defense in Depth**: RDS is inaccessible from the public internet. Access requires passing through EC2 or VPC-attached Lambda, authenticated via IAM and security groups.
2. **Zero-Trust OTP Storage**: Raw 6-digit OTPs are **never stored** in the database. Only one-way cryptographic bcrypt hashes (10 rounds) are persisted, rendering stolen database dumps useless for unauthorized package collection.
3. **Decoupled Asynchrony**: Drop-off operations complete in < 250ms because heavy crypto and notification dispatches are offloaded to an asynchronous SQS worker pipeline.
4. **Stateless Compute**: Neither EC2 nor Lambda hold stateful data locally. S3 handles objects, RDS handles state, and SSM handles credentials, allowing seamless instance replacement.
